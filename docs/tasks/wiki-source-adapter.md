# Задание: корпус `wiki` — нативный адаптер источника «Яндекс Вики»

> Самодостаточный бриф для сессии доработки `onec-vecgraph` (составлен из оркестратора
> «Full development pipeline», ветка `need-full-tests`). **Статус: не начато.**
> Все ссылки на код — по состоянию `main` @ `7a67e02`.

## Контекст

Сейчас документация из Яндекс Вики доступна ассистенту **только живым чтением** через MCP
`yandex_wiki` (:8021, v1.28.1): `wiki_get_page`, `wiki_list_subpages`, `wiki_search`. Это чтение
при каждом вопросе — без кэша, без семантического поиска по содержимому и без устойчивости к
недоступности API.

Векторизации вики нет и места под неё не предусмотрено: корпуса зафиксированы списком
`SUPPORTED_CORPORA` (`admin_server.py:38`), адаптеры источников — `DOC_SOURCE_TYPES`
(`sources/registry.py:9`), и **вся цепочка приёма документов файловая** — `index_corpus_tool`
принимает `manifest`, путь к YAML/JSON, существование которого проверяется на файловой системе
контейнера (`admin_server.py:172`). HTTP-загрузчика в ingest нет.

Рассматривался дешёвый путь (внешний экспортёр «раздел вики → каталог markdown + manifest» и
приём существующим корпусом `its`). **Отвергнут** — выбран нативный адаптер, чтобы иерархия
раздела хранилась честно, а не терялась в `section_path` ITS-типа.

## Цель

Корпус `wiki`: рекурсивная выгрузка раздела Яндекс Вики в тенант с инкрементальным обновлением,
запускаемая и наблюдаемая из UI оркестратора наравне с `its` / `dev_standards`.

## Что уже готово и править НЕ надо

Это самая полезная часть брифа: движок инкремента и вся обвязка корпусов переиспользуются как есть.

* **`ingest_source`** (`ingest.py:35`) — движок инкремента. Сравнивает `version_hash` каждой
  единицы с сохранённым, удаляет исчезнувшие, эмбеддит только изменившиеся, пишет владельцев и
  чанки, строит `MENTIONS`. Адаптеру достаточно отдавать `DocUnit` — **менять здесь ничего не
  нужно, кроме одного места, см. раздел про инкремент ниже**.
* **`Neo4jStore.doc_versions(tenant_id, source)`** (`storage/neo4j_store.py:260`) →
  `{owner_fqn: version_hash}`. Хранилище версий уже есть, отдельной таблицы заводить не надо.
* **`split_markdown_sections(text)`** (`sources/markdown.py`) — разбиение по заголовкам с
  хлебными крошками предков. Готово к переиспользованию для yfm (с оговоркой ниже).
* **`chunking.doc_chunks(...)`**, `_embed_and_write`, векторные и полнотекстовый индексы —
  вызываются из `ingest_source`, трогать не нужно.
* **Оркестратор**: фоновая очередь прогонов, прогресс, расписание, права и UI-карточка корпуса
  уже универсальны. Ветка `else` в `_build_index_call`
  (`pipeline_server/services/vectorize.py:867`) обслуживает любой корпус, работающий по
  `manifest`, а `idxCorpusInputs` (`pipeline_server/web/app.vectorize.js:394`) по умолчанию
  рисует поле `manifest`. **Если корпус `wiki` будет manifest-driven, правок в оркестраторе
  ровно две строки** (см. ниже).

## Контракт адаптера

`sources/base.py`. Подкласс задаёт три атрибута и один метод:

```python
class Source(ABC):
    name: str         # тип адаптера в манифесте, напр. 'wiki'
    source: str       # тег корпуса на чанках/владельцах, напр. 'wiki'
    owner_label: str  # метка узла-владельца: 'Document' | 'Artifact'

    def units(self) -> Iterator[DocUnit]: ...
```

```python
@dataclass
class DocUnit:
    external_id: str          # стабильный id ВНУТРИ источника → owner fqn и дедуп
    title: str
    text: str
    version_hash: str         # меняется только при смене содержимого → инкремент
    section_path: list[str]   # хлебные крошки для префикса чанка
    links: list[str]          # явные fqn конфигурации → рёбра MENTIONS
    source_url: str | None
    extra: dict               # произвольные свойства узла-владельца
```

`owner_fqn(source, external_id)` = `"<source>:<external_id>"` — ключ дедупа и удаления.
Всё из `extra` становится свойствами узла-владельца (`ingest.py:60`), это штатный способ протащить
свои поля (например `wiki_page_id`, `updated_at`, `author`).

Ближайший образец для копирования — `sources/git_artifacts.py` (markdown → секции → `DocUnit`),
он на 40 строк.

## ГЛАВНЫЙ РИСК: инкрементальность

Это тот же класс дефекта, который в этом проекте уже дважды приводил к суточным перестроениям
(см. `claude-work-history.md` оркестратора, записи 2026-07-28 и 2026-07-29). Прочитать до начала работы.

`ingest_source` устроен так:

```python
units = list(src.units())                       # ← материализует ВСЁ
current = {owner_fqn(src.source, u.external_id): u for u in units}
existing = store.doc_versions(tenant_id, src.source)
changed = [(f, u) for f, u in current.items() if existing.get(f) != u.version_hash]
```

Для файловых источников `list(src.units())` — это чтение с диска, дёшево. **Для вики это N
HTTP-запросов на каждый прогон, даже когда не изменилось ничего.** Инкремент в таком виде сэкономит
только эмбеддинг, но не выгрузку: холостая ночная волна будет ходить в API за всем разделом.

Три варианта, по возрастанию честности:

**A. Наивный (приемлем как v1).** `units()` тянет все страницы, `version_hash = sha1(текст секции)`.
Работает без правок движка. Приемлемо на сотнях страниц, неприемлемо на тысячах.

**B. Двухфазный (рекомендуется).** Если API отдаёт в листинге ревизию или `updated_at` —
`version_hash` считается из неё, и содержимое запрашивается **только для изменившихся**. Требует
одной правки движка: дать `Source` необязательный метод

```python
def versions(self) -> dict[str, str] | None:   # {external_id: version_hash}, None = не поддерживается
```

и в `ingest_source` — если `versions()` вернул словарь, сначала считать `changed` по нему, а
`units()` вызывать с фильтром по изменившимся id. Правка локальная, но затрагивает общий движок:
**обязательно прогнать на остальных корпусах**, они должны продолжать работать через ветку `None`.

**C. Вебхук.** Инкремент по событиям изменения страниц. Вне объёма этой задачи, но `extra` уже
позволяет сохранить `updated_at` на узле, чтобы потом было от чего оттолкнуться.

**Первое, что надо выяснить в новой сессии:** отдаёт ли API организации ревизию/`updated_at` в
листинге потомков. От этого зависит выбор A против B, и это определяет цену ночного расписания.
MCP-инструмент `wiki_list_subpages` отдаёт **только id+slug** — значит на его выдачу рассчитывать
нельзя, надо смотреть сырой API (`GET /pages/{id}/descendants` и соседние ручки).

## Прочие подводные камни

* **`external_id` — это ID страницы, а НЕ slug.** Страницы в вики переименовывают и переносят;
  у `wiki_get_page` даже есть отдельный параметр `resolve_moved` под это. Если взять slug, то
  каждый перенос = старая единица «удалена», новая «добавлена»: лишний эмбеддинг и потерянная
  история. ID стабилен и есть в листинге потомков.
* **Секции внутри страницы.** `git_artifacts` формирует `external_id` как `<путь>#<индекс секции>`.
  Индекс — позиционный, поэтому вставка абзаца в начало страницы сдвигает все последующие секции и
  переembedит страницу целиком. Для вики лучше брать якорь заголовка, а не индекс; при коллизиях
  заголовков — добавлять порядковый суффикс.
* **yfm ≠ markdown.** `split_markdown_sections` понимает только заголовки `#`. Блоки Яндекс-разметки
  (`{% cut %}`, `{% note %}`, таблицы, вставки) попадут в тело секции сырой разметкой и уедут в
  эмбеддинг как есть. Решить: вырезать, разворачивать или оставить. Молчаливое «оставить» ухудшит
  качество поиска незаметно.
* **Пагинация.** У MCP `wiki_list_subpages` `limit` по умолчанию 100 и параметра пагинации нет,
  есть `total_descendants` — размер поддерева до среза. В своём клиенте пагинацию надо
  реализовать честно и **сверять число выгруженных страниц с `total_descendants`**, иначе тихий
  срез будет выглядеть как успешная полная выгрузка (ровно тот же класс ошибки, что и выше).
* **Тестируемость без сети.** `tests/test_sources.py` — чистые юнит-тесты на `tmp_path`, ни одного
  сетевого вызова. Чтобы вписаться, у `WikiSource` должен быть шов для клиента (инъекция объекта
  клиента или `path` с заранее выгруженным фикстур-деревом, как `ItsSource` умеет читать локальный
  каталог вместо git). Спроектировать шов сразу, а не прикручивать к готовому адаптеру.
* **Права доступа.** Вики организации содержит страницы с ограниченным доступом. Токен адаптера
  увидит то, что видит его владелец, и всё это попадёт в общий тенант, доступный всем проектам.
  Решить до первой выгрузки, какой раздел индексируется и не утекут ли через семантический поиск
  страницы, которых пользователь не должен видеть. Это единственный пункт брифа с последствиями
  вне репозитория.

## Тесты

* `tests/test_sources.py` — единицы из фикстурного дерева страниц: заголовки → секции,
  `section_path` из иерархии раздела + заголовков, `external_id` не меняется при переименовании
  страницы, `version_hash` меняется только при смене содержимого.
* Инкремент: два прогона подряд по неизменному фикстуру → `changed == 0`; правка одной секции →
  `changed == 1`; удаление страницы → она попадает в `deleted`.
* Если выбран вариант B — тест, что корпуса без `versions()` (`its`, `git_artifacts`, `hbk`)
  продолжают идти прежним путём.

## Побочная находка (чинится вне этой задачи)

В реестре System оркестратора у `yandex_wiki` в `capabilities` перечислены только
`wiki_get_page` и `wiki_list_subpages`, а сервер отдаёт ещё и `wiki_search`. Выдать его роли
по-прежнему можно прямым грантом `tool:<имя>` (прекапабилити-фильтра в `build_routed_tools` нет),
но галочкой в UI он не показывается. Правится одной записью в реестре.
