# onec-lite — руководство пользователя

MCP-сервер по **живой рабочей копии** конфигурации 1С (выгрузка Конфигуратора **или** EDT-проект,
база + расширения) — **без Neo4j, без векторов, без GPU**. Источник истины — файлы на диске:
что сейчас в рабочей копии, то сервер и отдаёт. Поиск — ripgrep (+опц. FTS5-индекс),
анализ кода — BSL-парсер проекта.

Когда lite, а когда «большой» onec-vecgraph — см. [таблицу в конце](#lite-или-большой-сервер).

## Быстрый старт

Нужен только [uv](https://docs.astral.sh/uv/): `winget install astral-sh.uv`.

**Вариант А — двойной клик (Windows).** Откройте [`lite-admin.cmd`](../lite-admin.cmd) в корне
репозитория: поднимется сервер и в браузере откроется админка (`http://127.0.0.1:8010/admin`).
Укажите в форме путь к рабочей копии → «Применить и сохранить». Всё: пути запомнены
(`~/.onec-lite/config.json`), MCP-эндпоинт работает на `http://127.0.0.1:8010/mcp`.

**Вариант Б — одна команда из терминала** (из каталога репозитория или с `--directory`):

```powershell
uv run onec-lite admin                      # http + админка, браузер откроется сам
uv run onec-lite check                      # показать источники и выйти
uv run onec-lite                            # stdio MCP-сервер (для Claude Code — ниже)
```

**Вариант В — глобально, одним словом из любого места:**

```powershell
uv tool install --from "git+https://github.com/Ailirag/onec-vecgraph.git" onec-vecgraph
# при разработке самого сервера вместо URL допустим локальный путь к клону
uv tool update-shell     # один раз: добавить ~/.local/bin в PATH
onec-lite admin          # дальше — из любого каталога
```

### Выбор варианта развёртывания (по умолчанию — HTTP)

Два способа поднять сервер; **предпочтителен HTTP-сервис** — особенно для постоянного/общего
использования:

| Вариант | Как | Когда |
|---|---|---|
| **HTTP-сервис (рекомендуется)** | `uv run onec-lite admin` → эндпоинт `http://127.0.0.1:8010/mcp` | Постоянное использование: долгоживущий процесс + админка, один сервер на несколько проектов (явный аргумент `workspace`), FTS-индекс успевает собраться в фоне и остаётся тёплым между вызовами (prebuild всех воркспейсов на старте) |
| stdio per-session | `claude mcp add onec-lite -- uv run --directory "<репо>" onec-lite` | Разовая привязка к сессии/каталогу. Индекс строится лениво в фоне; на больших конфигурациях (напр. УТ) первая сборка может не завершиться за короткую сессию — она переживёт в `~/.onec-lite/fts/` и достроится позже |

Набор инструментов одинаков; разница — в жизненном цикле процесса и готовности FTS-индекса.
К HTTP-эндпоинту клиент подключается по `http://127.0.0.1:8010/mcp` (Streamable HTTP);
несколько проектов на одном сервере — [ниже](#один-http-сервер-на-несколько-проектов-явный-аргумент).

> **Агенту-установщику:** не выбирай способ молча. **Явно предложи пользователю** HTTP-сервис
> (по умолчанию) либо stdio per-session и подтверди выбор, прежде чем регистрировать MCP.
> Для HTTP-варианта проверь `uv`, установи пакет, запусти сервис на loopback, проверь
> `/admin.json`, затем зарегистрируй URL и правило явного `workspace` для каждого вызова.
> Пути проекта, БСП, справки, `rg.exe`, FTS и нестандартные каталоги кешей в Git не коммить.

### Подключение к Claude Code (рекомендованный стандарт)

Держим **один HTTP-сервер** (`onec-lite admin` → `http://127.0.0.1:8010/mcp`) и подключаем
клиентов по URL в project-scope `.mcp.json`:

```json
{ "mcpServers": { "onec-lite": {
  "type": "http", "url": "http://127.0.0.1:8010/mcp"
} } }
```

**Строгий контракт выбора:** сначала `list_workspaces()`, затем явный `workspace="ut"`
в **каждом** другом MCP-вызове (например, `overview(workspace="ut")`). Это обязательно и
для единственного воркспейса, и для `platform_*`/`list_kinds`, во всех профилях и транспортах.
Пропуск, `null`, нестроковое, пустое, пробельное или неизвестное имя отклоняются до доступа
к данным/кэшам/индексам/git. Схемы tools/list публикуют workspace как required string.
Заголовки `X-Workspace`/`X-Tenant-Id` (включая настроенный альтернативный заголовок), env,
`--workspace` и active **не подставляются** вместо аргумента.
Инициализация протокола, tools/list и `list_workspaces()` доступны без выбора.

В `CLAUDE.md` проекта запишите: «В каждом вызове onec-lite передавай workspace="ut"».
Если имя неоднозначно, агент должен спросить пользователя, а не угадывать. К другой
конфигурации обращаться только по явной просьбе пользователя.

Альтернатива (разовая привязка, отдельный процесс на сессию) — stdio:

```bash
claude mcp add onec-lite --scope user -- uv run --directory "D:\путь\к\репозиторию" onec-lite
```

(с глобальной установкой — `claude mcp add onec-lite --scope user -- onec-lite`; проверка —
`claude mcp get onec-lite` → `Connected`).

## Настройка

Один раз в админке (`onec-lite admin`) — всё сохраняется и переживает рестарты:

| Поле | Что указывать |
|---|---|
| Корень конфигурации | Каталог выгрузки Конфигуратора (где `Configuration.xml`) **или** EDT-воркспейс (каталог с проектами; расширения находятся автоматически) |
| Корни расширений | Только для нестандартно расположенных расширений — по одному пути в строке |
| Корпуса БСП | Корни XML-выгрузок или EDT workspace нужных версий БСП; индексируются только для `fts_search`, не подмешиваются в метаданные проекта |
| Справка платформы | Каталог `bin` установленной платформы или файл `.hbk`; строка вида `8.3.27=C:\...\bin` задаёт версию явно; несколько строк = несколько версий; настройка принадлежит выбранному воркспейсу |
| Путь к ripgrep | Обычно не нужно (ищется в PATH/WinGet/VS Code); поле — если rg лежит нестандартно |

Кнопки: **«Применить и сохранить»** — переключение путей на лету, без рестарта;
**«Построить индекс поиска»** (FTS5) и **«Построить индексы» справки** — см. [Индексы](#индексы);
**«Сбросить кэши»** — принудительно перечитать всё с диска (обычно не нужно: кэши сами
инвалидируются по mtime/TTL ≤15 с).

То же самое через переменные окружения (приоритет: CLI-аргументы → env → сохранённое состояние):

| Переменная | Смысл (дефолт) |
|---|---|
| `ONEC_LITE_ROOT` / `ONEC_LITE_EXT_ROOTS` | корень / доп. корни расширений через `;` |
| `ONEC_LITE_WORKSPACE` | имя воркспейса для CLI/админки; не дефолт MCP-вызовов (см. [Несколько конфигураций](#несколько-конфигураций-воркспейсы)) |
| `ONEC_LITE_WORKSPACE_HEADER` | legacy-настройка внутренних помощников; для выбора в MCP больше не используется |
| `ONEC_LITE_HELP` | пути справки через `;` (форма `версия=путь` допустима) |
| `ONEC_LITE_ADMIN` | `true` = включить админку (или флаг `--admin` / режим `admin`) |
| `ONEC_LITE_HOST` / `ONEC_LITE_PORT` | HTTP-биндинг (`127.0.0.1` / `8010` — не конфликтует с докерным big-сервером на `:8000`) |
| `ONEC_LITE_RG` | явный путь к `rg.exe` |
| `ONEC_LITE_STATE` | файл состояния (`~/.onec-lite/config.json`) |
| `ONEC_LITE_PROFILE` | состав публикуемых инструментов: `lean` (по умолчанию) / `full` / `review` — см. ниже |
| `ONEC_LITE_DISABLED_TOOLS` | точечно убрать инструменты (список через запятую/пробел), поверх профиля |

### Состав инструментов: профили

Схемы инструментов уходят клиенту в системном промпте **на каждый запрос**, поэтому состав — это
цена сессии, а не косметика (замер токенизатором cl100k):

| Профиль | Тулов | Схемы + инструкции | Когда |
|---|---|---|---|
| `lean` (по умолчанию) | 23 | ≈ 9 500 токенов | Обычная работа: у агента есть Grep/ripgrep, чтение файлов и git |
| `full` | 32 | ≈ 12 000 токенов | У агента нет шелла и чтения файлов (ограниченный раннер) — тогда `search_code`/`read_file`/`read_module` единственный путь |
| `review` | 11 | ≈ 6 500 токенов | Только код-ревью: «что я сломал этой правкой» + проверка объекта |

Из `lean` убраны инструменты, дублирующие то, что у агента уже есть, причём **дешевле**:
`search_code`/`search_metadata` (тонкие обёртки над rg), `list_routines`, `read_file`/`read_module`,
`changed_objects`, `list_objects`, `list_kinds`, `metrics`. Они **не удалены** — включаются
профилем `full`; чем именно заменять каждый, см. [«rg или MCP»](#rg-или-mcp-карта-маршрутизации).

Что остаётся всегда: то, что поиском по тексту выразить нельзя — `find_callers`/`find_callees`/
`call_graph` (вызов против объявления), `find_overrides` (принадлежность перехвата объекту),
`get_object`/`writes_to` (слияние базы с расширениями, типы, обязательность, движения),
`read_routine` (границы рутины), `fts_search` (ранжированный NL-запрос), `find_routine` (полный
счёт объявлений и порядок по значимости), `find_handlers`, `find_type_usages`,
`get_form`/`get_service`, `review_set`, `overview`, `list_workspaces`.

Админка не аутентифицируется — держите её на loopback (дефолт) или за прокси.

**ripgrep (ускорение поиска).** Порядок поиска rg: `ONEC_LITE_RG` → **бандл в установке**
(`~/.onec-lite/bin/rg[.exe]` или `<пакет>/lite/vendor/rg[.exe]`) → PATH → WinGet / cargo /
chocolatey → ripgrep из VS Code. Чтобы «зашить» rg в установку и не зависеть от PATH — положите
бинарь в `~/.onec-lite/bin/`. Без rg всё работает на Python-фолбэке, но на больших
конфигурациях заметно медленнее (`find_callers`/`call_graph`/`search_code`).

## Несколько конфигураций (воркспейсы)

Один lite-сервер держит **несколько рабочих копий** как именованные воркспейсы: таблица в
админке (добавить = новое имя в форме путей; «активировать»/«удалить»), сохраняются в общем
state-файле; FTS-индексы, корпуса БСП и справка платформы раздельны по workspace. Общим
остаётся только путь к `rg` — это исполняемый файл машины, а не знания проекта.

Процесс разработки может регистрировать workspace без ручной формы через
`POST /admin/workspace` (админка должна быть включена): JSON принимает `name`, `root`,
`ext_roots`, `platform_help`, `bsp_roots` и необязательный `build`. Без `build` FTS
дообновляется в фоне. Это рекомендуемый путь для проектных `.1c-workflow.json`: две
конфигурации с разными версиями платформы/БСП не должны делить глобальный корпус.

Каждый MCP-инструмент, кроме `list_workspaces()`, требует явный `workspace=<имя>`.
Никакого порядка подстановки значений для MCP нет. `list_workspaces().default_workspace`
всегда пуст; `active` — только отметка оператора.

### Как указать сессии Клода нужную конфигурацию

В `CLAUDE.md` проекта:

```markdown
## Конфигурация 1С
Работаем с УТ: во всех инструментах onec-lite передавай workspace="ut".
Начни с list_workspaces() и overview(workspace="ut").
Без явного аргумента сервер откажет, даже если задан заголовок или env.
```

Для разовой работы достаточно такой же просьбы в чате. Пример сравнения по явному запросу
пользователя: `get_object(kind="Catalog", name="Товары", workspace="erp")`.

`onec-lite --root X --workspace ut` по-прежнему конфигурирует корень под именем `ut`;
CLI `check`/`update` и админка сохраняют свои предвыборы. Но stdio MCP-вызовы в этом процессе
тоже обязаны передавать `workspace="ut"`. Прямые Python-вызовы внутренних функций оставлены
для совместимости CLI/админки; строгая проверка стоит на общей границе регистрации MCP.

### Один http-сервер на несколько проектов (явный аргумент)

Один URL `…/mcp` обслуживает все проекты. Клиент/оркестратор должен включать имя выбранного
воркспейса в `tools/call.params.arguments.workspace` **при каждом вызове**. Одного
`tenant_header: X-Tenant-Id`, `X-Workspace` или custom header больше недостаточно.
Перенесите выбор из настройки заголовка в аргументы инструментов/инструкции проекта.
Пример JSON-RPC:

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"overview","arguments":{"workspace":"ut"}}}
```

Справка `platform_*` проходит ту же проверку известного имени, но не загружает рабочую
копию ради проверки. Для MCP настройте именованный воркспейс и его корпус справки;
старый глобальный help-only режим без зарегистрированных воркспейсов остаётся доступен
через CLI/админку, но не обходит строгий MCP-контракт.

## Обновление рабочих копий из remote

Зеркала для анализа протухают тихо — поэтому обновление настраивается, но всегда явно
и с предохранителями (MCP-поверхность остаётся строго read-only, как у большого сервера):

| Операция | Что делает | Безопасность |
|---|---|---|
| `fetch` | обновляет только `origin/*` (нужен для честного `review_set(ref="origin/…")`) | безопасен всегда, дерево не трогает |
| `pull` | `git pull --ff-only` | отменяется, если: не git-репо, дерево не чистое, HEAD не на ветке, история разошлась |
| **зеркало** | воркспейс задаётся git-URL (`repo` + ветка) вместо пути — lite сам клонирует (полная история) в `~/.onec-lite/mirrors/<имя>` и обновляет | клоном владеет lite, pull безопасен всегда |

Где настраивается и запускается:

- **Админка**: в форме воркспейса — поле «git-URL зеркала», ветка и селектор
  «Обновление при старте» (выключено / fetch / pull); в таблице воркспейсов — кнопка
  **«обновить»** (зеркало → clone/pull, путь → fetch) и git-статус (ветка, «грязное
  дерево», «отстаёт на N», итог последнего обновления).
- **CLI (разово)**: `onec-lite update [--workspace имя]` — fetch; `--pull` — обновить дерево.
- **CLI (демон)**: `onec-lite sync --interval N | --at HH:MM [--pull] [--once]` — отдельный
  процесс, периодически обновляющий ВСЕ воркспейсы (зеркало → clone/pull, путь → fetch, с
  `--pull` — ff-pull дерева пути). Расписание на stdlib (без зависимостей): `--interval` (сек,
  дрейфонезависимо) или `--at HH:MM` (повторяемый, фикс. время суток; приоритетнее interval).
  `--once` — один проход и выход (для внешнего cron/systemd). Индексы не строит — обслуживающий
  сервер догонит FTS по mtime; `--workspace` ограничивает набор.
- **`update_on_start`** — выполняется один раз при первом обращении процесса к
  воркспейсу; ошибка не блокирует работу (обслуживается то, что на диске), итог виден
  в админке.

Все git-вызовы неинтерактивны (`GIT_TERMINAL_PROMPT=0`): недоступный remote или
отсутствие кредов дают быстрый понятный отказ, а не зависший сервер. Индексы ничего
не требуют: кэши и FTS дообновятся по mtime сами. Сам MCP-сервер по таймеру ничего не
обновляет — намеренно, чтобы код не менялся под ногами агента посреди анализа; периодическое
обновление вынесено в отдельный процесс `onec-lite sync` (обновляет рабочие копии, но не индексы) —
его стоит нацеливать на окна/паузы между анализами (`--at`), а на проде запускать сайдкаром
рядом с MCP-сервером.

## Инструменты (30)

Имя источника (`source`) — из `overview()`; пусто = все источники, **расширения раньше базы**
(для заимствованных объектов есть фолбэк в базу). `module` — `Module|Object|Manager|RecordSet|
Value|Command|Form:<Имя>`. Все MCP-инструменты, кроме `list_workspaces`, требуют
непустой явный `workspace=<имя>` (включая `list_kinds` и `platform_*`).

**Обзор и структура**

| Инструмент | Зачем |
|---|---|
| `list_workspaces` | рабочие копии сервера: имена, корни, отметка active; default_workspace всегда пуст (работает без выбора) |
| `overview` | источники (база+расширения) и объекты по видам |
| `list_kinds` | допустимые `kind` (+русские названия) |
| `list_objects` | объекты вида, фильтр по подстроке имени |
| `get_object` | карточка объекта: реквизиты, ТЧ, формы, модули, движения; `detail=true` — полный сырой набор свойств |
| `metrics` | инвентарь: объекты/файлы/байты кода/рутины/override-аннотации |

**Чтение кода**

| | |
|---|---|
| `list_routines` | процедуры/функции модуля: сигнатуры, Экспорт, директивы, точки входа, override-аннотации |
| `read_module` / `read_routine` | текст модуля с пагинацией / тело одной рутины |
| `read_file` | любой файл источника (`.mdo`, `.form`, `.xml`, `.bsl`) |

**Поиск** (что выбрать — [ниже](#rg-или-mcp-карта-маршрутизации))

| | |
|---|---|
| `search_code` | точный текст/regex по BSL (ripgrep; без rg — медленный Python-фолбэк) |
| `fts_search` | ранжированный BM25-поиск по рутинам и карточкам объектов (требует построенного индекса) |
| `search_metadata` | объекты по имени и тексту метаданных (синонимы) |
| `find_routine` | где ОБЪЯВЛЕНА процедура/функция с этим именем; сужение по объекту — `object_hint` или `kind`+`name` |
| `bsl_sql` | произвольный SELECT по индексу рутин и вызовов (агрегаты); пустой `sql` отдаёт схему |

**Анализ кода** — гибрид «rg сужает кандидатов → BSL-парсер подтверждает»

| | |
|---|---|
| `find_callers` | места вызова рутины (объявления/строки/комментарии исключены; `object_hint` отсекает одноимённые) |
| `find_callees` | кого вызывает рутина: local/common_module/manager с confidence |
| `call_graph` | восходящий граф «кто (рекурсивно) вызывает» |
| `find_handlers` | события форм объекта (+объявлен ли обработчик), точки входа модулей (проведение/запись/…), подписки на события |
| `find_overrides` | переопределения расширений `&Вместо/&Перед/&После/&ИзменениеИКонтроль` с целями |
| `writes_to` | документ → регистры; регистр → кто в него пишет |

**Метаданные и интеграции**

| | |
|---|---|
| `get_dependencies` | связи объекта: ссылочные реквизиты, владельцы, движения, подписки |
| `find_type_usages` | где используется ТИП объекта (реквизиты, определяемые типы, подписки) |
| `get_service` | HTTPService (rootURL, шаблоны URL, методы+обработчики) / WebService (операции) |
| `get_form` | структура формы: реквизиты, команды, элементы (dataPath/commandName), обработчики |
| `get_template` | макет объекта разобранный: для СКД — наборы данных, поля, параметры, запрос; для прочих — путь для `read_file` |

**Git-осведомлённость** (рабочая копия — git-репозиторий)

| | |
|---|---|
| `changed_objects` | что изменено: git status или diff против `ref` (ветки/коммита) → объекты и модули |
| `review_set` | ревью-набор: изменённые строки → затронутые рутины → их вызывающие + обработчики + overrides |

**Справка платформы** (синтаксис-помощник из `.hbk`, без векторов)

| | |
|---|---|
| `platform_docinfo` | точный лукап темы: «Массив.Найти», «Array.Find», короткое имя с дизамбигуацией |
| `platform_search` | FTS5-поиск по названиям RU/EN и полному тексту тем; фильтр по сборке |
| `platform_get_document` | полный текст темы (без версии — самая свежая сборка) |
| `platform_versions` | какие сборки загружены и сколько тем |

## Типовые сценарии

- **«Что за объект и как устроен»**: `get_object` → `list_routines` → `read_routine`.
- **«Где считается X»** (формулировка словами): `fts_search("расчет себестоимости")` — BM25
  выведет расчётные рутины наверх. Точная строка/идентификатор — `search_code`.
- **Ревью своей ветки**: `changed_objects(ref="origin/main")` → `review_set(ref="origin/main")` —
  сразу видно, какие рутины задеты, кто их вызывает и какие обработчики/overrides рядом.
- **Импакт правки структуры**: `find_type_usages` + `get_dependencies` + `writes_to(register=...)`.
- **Расширение против базы**: `find_overrides(kind, name)` → `read_routine(..., source="<расширение>")`.
- **API платформы**: `platform_docinfo("ТаблицаЗначений.Найти")`; не помните имя или
  знаете только формулировку «как сделать» — `platform_search`.

## Индексы

| Индекс | Что даёт | Цена (реальная УТ: база + 2 расширения) | Обновление |
|---|---|---|---|
| FTS5 (`fts_search`) | ранжированный поиск по ~267k рутин/карточек; точный FQN и полнота термов переранжируют top-BM25 | ~3.4 мин, ~1 ГБ в `~/.onec-lite/fts/` | инкремент по mtime; авто-дообновление при поиске (раз в ≥30 с), `built_at` в каждом ответе |
| Справка платформы | точный лукап + FTS5 по названию/тексту ~25k тем на версию | замер 8.3.27: ~6.5 с первая сборка, пик ~149 МБ | отдельный дисковый индекс на запрошенную сборку; инвалидация по пути, размеру и mtime `.hbk` |

Оба индекса живут **вне рабочей копии** в каталоге `fts_dir` — `git status` разработчика остаётся чистым.
Без построенного FTS-индекса `fts_search` вернёт понятную ошибку, остальное работает.

## rg или MCP: карта маршрутизации

Правило в одну строку: нужен **разбор** BSL/метаданных 1С — MCP; нужен **текст** или **счёт
вхождений** — ripgrep. Эта же карта лежит в `instructions` сервера, так что агент получает её без
участия человека. Замеры — на УТ (15 тыс. модулей, база + 4 расширения), токены — cl100k.

**Через MCP** — rg этого не может или ответит неверно:

| Инструмент | Чего нет у rg |
|---|---|
| `find_callers` `call_graph` `find_callees` | Отличает вызов от объявления и от комментария: у наивного rg на популярном методе 18 из 20 строк — объявления. Полный счёт (`call_rows_total`, `distinct_callers`) и точная строка вызова |
| `find_overrides` | Связывает `&Вместо` с целевым объектом; текстом аннотация найдётся, привязка — нет |
| `get_object` | Слияние базы с расширениями: заимствованный объект лежит огрызком, rg покажет 2–3 копии и оставит выбор вам. Типы, обязательность, ТЧ |
| `writes_to` | Движения документа со слиянием (1 регистр в базе + 3 в расширении = верный ответ 4) |
| `read_routine` | Границы рутины — модули 1С не влезают в лимит чтения целиком |
| `fts_search` | Ранжирование NL-запроса: нужный метод место 1 против 21-го из 535 у rg |
| `find_routine` | Полный счёт объявлений и порядок по значимости — так находится настоящий обработчик среди тысяч одноимённых |
| `bsl_sql` | Агрегаты одним `GROUP BY` вместо выдачи строками: 462 токена против 37 437 на том же вопросе |
| `get_template` | Схема компоновки структурой, а не разметкой: 5 741 токен против 23 455 у чтения макета целиком |
| `find_type_usages` | Полный счёт использований типа (`usage_count`) без доплаты за проход |
| `find_handlers` | Привязка обработчиков форм и точки входа |
| `review_set` | Единственный, кто мапит ханки диффа → рутины → их вызывающих |
| `get_form` `get_service` | Структура из XML: элементы, команды, обработчики, шаблоны URL |
| `overview` | Карта источников + предупреждение о **неподключённых** расширениях |

**Прямым rg** — дешевле в 2–25 раз:

| Задача | Команда | Выигрыш |
|---|---|---|
| Текст, подстрока, regex | `rg -n "<regex>" <корни>` | вместо `search_code` |
| Объект по имени в метаданных | `rg -n -g "*.mdo" -e "<Имя>" <корни>` | вместо `search_metadata` |
| Агрегат «сколько и где» | `bsl_sql` — один `GROUP BY` по индексу | **×81** дешевле `find_callers` (462 ток. против 37 437 на УТ) |
| Объявление, когда хватит первой находки | `rg -n "^\s*(Процедура\|Функция)\s+<Имя>" <корни>` | ×2.5 |
| Состав методов известного модуля | `rg -n "^\s*(Процедура\|Функция)" <файл>` | ×3.5 (вместо `list_routines`) |
| Что изменилось | `git diff --name-status <ref>` | ×5 (вместо `changed_objects`) |
| Чтение известного файла или окна строк | обычное чтение файла | вместо `read_file`/`read_module` |
| Первый разведочный вопрос | rg | MCP платит прогрев ~1.6 с и постоянные схемы |

**Пограничные случаи.** `changed_objects` берите, когда нужна группировка путей по объектам
метаданных (сам дифф дешевле у git). `get_object` по токенам примерно в паритете с грамотным rg
(×0.85), но для заимствованного объекта берите всегда — иначе сливать копии руками.

> **Ловушка.** Корни для rg берите из `overview()`: база и **каждое** расширение — отдельный
> корень. Запуск rg только в `conf/` теряет до **75 %** результатов (у одного метода 3 из 4
> вызывающих лежали в расширениях). MCP-инструменты учитывают источники сами.

**Экономика без иллюзий.** По токенам MCP дороже компетентного rg в ~2.2 раза (2.6 с учётом
постоянной платы за схемы). Выигрыш — скорость ×2 на кодовых вопросах и проверенность ответа.
Отсюда и карта: MCP там, где неверный ответ дороже токенов; rg там, где вопрос сводится к тексту.
Для смыслового поиска с синонимией и документации ИТС — **большой** сервер (`hybrid_search`).

## Траблшутинг

| Симптом | Решение |
|---|---|
| `search_code` медленный, в ответе `engine: python` | ripgrep не найден: `winget install BurntSushi.ripgrep.MSVC`, либо путь в админке / `ONEC_LITE_RG` |
| «Workspace не сконфигурирован» | `onec-lite admin` → задать корень; или `--root` / `ONEC_LITE_ROOT` |
| Порт 8010 занят | `onec-lite admin --port 8011` (или `ONEC_LITE_PORT`) |
| «FTS5 недоступен в этой сборке Python» | редкая сборка sqlite3 без FTS5 — используйте `search_code`, остальное не затронуто |
| Правки не видны | кэши инвалидируются по mtime/TTL ≤15 с; мгновенно — «Сбросить кэши» в админке |
| Админка отвечает 404 | она opt-in: режим `admin`, флаг `--admin` или `ONEC_LITE_ADMIN=true`; транспорт http |

## Совместная работа с большим сервером

Большой onec-vecgraph и так работает со **всеми** репозиториями сразу — они живут арендаторами
в одном Neo4j, арендатор выбирается заголовком `X-Tenant-Id`/bearer-токеном при регистрации.
Типовая связка в сессии: **lite = живая копия текущего репо** (свежесть, git, ревью ветки),
**big = все конфигурации разом** (семантический поиск, ИТС/стандарты, кросс-конфигурационные
вопросы). Регистрируются оба; big можно так же приколоть к проекту через project-scope
с разными токенами. Подробности подключения big — [MCP_USAGE.md](MCP_USAGE.md).

## Lite или большой сервер?

| | onec-lite | onec-vecgraph (big) |
|---|---|---|
| Данные | живая рабочая копия, всегда свежие | снимок в Neo4j (индексация оператором) |
| Инфраструктура | нет (uv + stdio/http) | Docker: Neo4j ~12 ГБ RAM, GPU для векторизации |
| Поиск | rg + FTS5 BM25 (лексический) | векторный + полнотекст + RRF (семантика) |
| Кому | разработчик на своей машине, ревью ветки | команда/агенты: BA, СА, архитектор, ревьюер |
| Уникальное | git-осведомлённость, `get_service`/`get_form`, нулевой старт | ИТС/артефакты/стандарты, мультиарендность+auth, GraphRAG, `:Detail`, overlay |
| Гид | этот документ | [MCP_USAGE.md](MCP_USAGE.md) |

Они не конкурируют: lite — «здесь и сейчас» у разработчика, big — общая память команды.
Один и тот же BSL-парсер и парсеры метаданных гарантируют согласованность результатов.
