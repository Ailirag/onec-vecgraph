# onec-lite — руководство пользователя

MCP-сервер по **живой рабочей копии** конфигурации 1С (выгрузка Конфигуратора **или** EDT-проект,
база + расширения) — **без Neo4j, без векторов, без GPU**. Источник истины — файлы на диске:
что сейчас в рабочей копии, то сервер и отдаёт. Поиск — ripgrep (+опц. FTS5-индекс),
анализ кода — BSL-парсер проекта.

Когда lite, а когда «большой» onec-vecgraph — см. [таблицу в конце](#lite-или-большой-сервер).

## Быстрый старт

Нужен только [uv](https://docs.astral.sh/uv/): `winget install astral-sh.uv`.

**Вариант А — двойной клик (Windows).** Откройте [`lite-admin.cmd`](../lite-admin.cmd) в корне
репозитория: поднимется сервер и в браузере откроется админка (`http://127.0.0.1:8010/admin`).
Укажите в форме путь к рабочей копии → «Применить и сохранить». Всё: пути запомнены
(`~/.onec-lite/config.json`), MCP-эндпоинт работает на `http://127.0.0.1:8010/mcp`.

**Вариант Б — одна команда из терминала** (из каталога репозитория или с `--directory`):

```powershell
uv run onec-lite admin                      # http + админка, браузер откроется сам
uv run onec-lite check                      # показать источники и выйти
uv run onec-lite                            # stdio MCP-сервер (для Claude Code — ниже)
```

**Вариант В — глобально, одним словом из любого места:**

```powershell
uv tool install --from "D:\путь\к\репозиторию" onec-vecgraph
uv tool update-shell     # один раз: добавить ~/.local/bin в PATH
onec-lite admin          # дальше — из любого каталога
```

### Подключение к Claude Code

Пути уже настроены через админку (вариант А/Б), поэтому регистрация — без аргументов:

```bash
claude mcp add onec-lite --scope user -- uv run --directory "D:\путь\к\репозиторию" onec-lite
```

(с глобальной установкой — просто `claude mcp add onec-lite --scope user -- onec-lite`).
Проверка: `claude mcp get onec-lite` → `Connected`. Явные пути, если админкой не пользуетесь:
`... -- onec-lite --root "H:\path\to\ut"`.

## Настройка

Один раз в админке (`onec-lite admin`) — всё сохраняется и переживает рестарты:

| Поле | Что указывать |
|---|---|
| Корень конфигурации | Каталог выгрузки Конфигуратора (где `Configuration.xml`) **или** EDT-воркспейс (каталог с проектами; расширения находятся автоматически) |
| Корни расширений | Только для нестандартно расположенных расширений — по одному пути в строке |
| Справка платформы | Каталог `bin` установленной платформы или файл `.hbk`; строка вида `8.3.27=C:\...\bin` задаёт версию явно; несколько строк = несколько версий |
| Путь к ripgrep | Обычно не нужно (ищется в PATH/WinGet/VS Code); поле — если rg лежит нестандартно |

Кнопки: **«Применить и сохранить»** — переключение путей на лету, без рестарта;
**«Построить индекс поиска»** (FTS5) и **«Построить индексы» справки** — см. [Индексы](#индексы);
**«Сбросить кэши»** — принудительно перечитать всё с диска (обычно не нужно: кэши сами
инвалидируются по mtime/TTL ≤15 с).

То же самое через переменные окружения (приоритет: CLI-аргументы → env → сохранённое состояние):

| Переменная | Смысл (дефолт) |
|---|---|
| `ONEC_LITE_ROOT` / `ONEC_LITE_EXT_ROOTS` | корень / доп. корни расширений через `;` |
| `ONEC_LITE_WORKSPACE` | имя воркспейса — дефолт этого процесса/сессии (см. [Несколько конфигураций](#несколько-конфигураций-воркспейсы)) |
| `ONEC_LITE_HELP` | пути справки через `;` (форма `версия=путь` допустима) |
| `ONEC_LITE_ADMIN` | `true` = включить админку (или флаг `--admin` / режим `admin`) |
| `ONEC_LITE_HOST` / `ONEC_LITE_PORT` | HTTP-биндинг (`127.0.0.1` / `8010` — не конфликтует с докерным big-сервером на `:8000`) |
| `ONEC_LITE_RG` | явный путь к `rg.exe` |
| `ONEC_LITE_STATE` | файл состояния (`~/.onec-lite/config.json`) |

Админка не аутентифицируется — держите её на loopback (дефолт) или за прокси.

## Несколько конфигураций (воркспейсы)

Один lite-сервер держит **несколько рабочих копий** как именованные воркспейсы: таблица в
админке (добавить = новое имя в форме путей; «активировать»/«удалить»), сохраняются в общем
state-файле; FTS-индексы и так раздельные на каждый корень, справка платформы и rg — общие.

Каждый инструмент принимает `workspace=<имя>` (список — `list_workspaces()`); пусто = дефолт,
который резолвится так: **env `ONEC_LITE_WORKSPACE` → активный из админки → единственный**.

**Разные сессии Claude Code — разные конфигурации** (главный сценарий): регистрируйте lite
на уровне проекта — в каталоге каждого 1С-репозитория один раз:

```bash
# в каталоге проекта УТ:
claude mcp add onec-lite --scope project -- uv run --directory "<репо vecgraph>" onec-lite --workspace ut
# в каталоге ERP:
claude mcp add onec-lite --scope project -- uv run --directory "<репо vecgraph>" onec-lite --workspace erp
```

Сессия, открытая в каталоге УТ, автоматически говорит с воркспейсом `ut`, сессия в ERP — с
`erp` (у каждой свой процесс, свои 29+ инструментов, ничего не пересекается). Пути каждого
воркспейса задаются один раз в админке. Внутри любой сессии можно обратиться к чужому:
`get_object(..., workspace="erp")` — например, сравнить реализацию УТ и ERP в одном чате.

`onec-lite --root X --workspace ut` конфигурирует корень под именем `ut` и делает его
дефолтом процесса; `onec-lite admin` показывает и редактирует все воркспейсы разом.

### Как указать сессии Клода нужную конфигурацию

По убыванию надёжности:

1. **Привязка к каталогу** — project-scope-регистрация с `--workspace` (рецепт выше):
   сессия в этом каталоге всегда говорит с нужной конфигурацией, просить не нужно.
   Нюанс: в корне появится `.mcp.json` — добавьте в `.gitignore` репозитория 1С
   (или закоммитьте намеренно, чтобы настройку получила вся команда).
2. **Инструкция в `CLAUDE.md` проекта** — когда сессии живут не в каталоге рабочей копии:

   ```markdown
   ## Конфигурация 1С
   Работаем с УТ: во всех инструментах onec-lite передавай workspace="ut"
   (активный дефолт сервера может указывать на другую конфигурацию).
   ```

3. **Просьба в чате** — для разового. Называйте воркспейс его именем и просите
   проверить: «Работай с воркспейсом **ut** (onec-lite): начни с `list_workspaces`
   и `overview(workspace="ut")`, дальше все вызовы — с `workspace="ut"`». Для
   разового заглядывания в соседнюю конфигурацию достаточно «сравни с воркспейсом mdm».

«Активный» воркспейс из админки — общий дефолт на всех: удобен, когда долго работаете
с одной конфигурацией, но при параллельных сессиях по разным — полагайтесь на п. 1–2,
а не на него.

## Инструменты (30)

Имя источника (`source`) — из `overview()`; пусто = все источники, **расширения раньше базы**
(для заимствованных объектов есть фолбэк в базу). `module` — `Module|Object|Manager|RecordSet|
Value|Command|Form:<Имя>`. Все инструменты (кроме `list_kinds` и `platform_*`) принимают
`workspace=<имя>` — пусто = дефолт сессии.

**Обзор и структура**

| Инструмент | Зачем |
|---|---|
| `list_workspaces` | рабочие копии сервера: имена, корни, активная, дефолт сессии |
| `overview` | источники (база+расширения) и объекты по видам |
| `list_kinds` | допустимые `kind` (+русские названия) |
| `list_objects` | объекты вида, фильтр по подстроке имени |
| `get_object` | карточка объекта: реквизиты, ТЧ, формы, модули, движения; `detail=true` — полный сырой набор свойств |
| `metrics` | инвентарь: объекты/файлы/байты кода/рутины/override-аннотации |

**Чтение кода**

| | |
|---|---|
| `list_routines` | процедуры/функции модуля: сигнатуры, Экспорт, директивы, точки входа, override-аннотации |
| `read_module` / `read_routine` | текст модуля с пагинацией / тело одной рутины |
| `read_file` | любой файл источника (`.mdo`, `.form`, `.xml`, `.bsl`) |

**Поиск** (что выбрать — [ниже](#какой-поиск-выбрать))

| | |
|---|---|
| `search_code` | точный текст/regex по BSL (ripgrep; без rg — медленный Python-фолбэк) |
| `fts_search` | ранжированный BM25-поиск по рутинам и карточкам объектов (требует построенного индекса) |
| `search_metadata` | объекты по имени и тексту метаданных (синонимы) |
| `find_routine` | где ОБЪЯВЛЕНА процедура/функция с этим именем |

**Анализ кода** — гибрид «rg сужает кандидатов → BSL-парсер подтверждает»

| | |
|---|---|
| `find_callers` | места вызова рутины (объявления/строки/комментарии исключены; `object_hint` отсекает одноимённые) |
| `find_callees` | кого вызывает рутина: local/common_module/manager с confidence |
| `call_graph` | восходящий граф «кто (рекурсивно) вызывает» |
| `find_handlers` | события форм объекта (+объявлен ли обработчик), точки входа модулей (проведение/запись/…), подписки на события |
| `find_overrides` | переопределения расширений `&Вместо/&Перед/&После/&ИзменениеИКонтроль` с целями |
| `writes_to` | документ → регистры; регистр → кто в него пишет |

**Метаданные и интеграции**

| | |
|---|---|
| `get_dependencies` | связи объекта: ссылочные реквизиты, владельцы, движения, подписки |
| `find_type_usages` | где используется ТИП объекта (реквизиты, определяемые типы, подписки) |
| `get_service` | HTTPService (rootURL, шаблоны URL, методы+обработчики) / WebService (операции) |
| `get_form` | структура формы: реквизиты, команды, элементы (dataPath/commandName), обработчики |

**Git-осведомлённость** (рабочая копия — git-репозиторий)

| | |
|---|---|
| `changed_objects` | что изменено: git status или diff против `ref` (ветки/коммита) → объекты и модули |
| `review_set` | ревью-набор: изменённые строки → затронутые рутины → их вызывающие + обработчики + overrides |

**Справка платформы** (синтаксис-помощник из `.hbk`, без векторов)

| | |
|---|---|
| `platform_docinfo` | точный лукап темы: «Массив.Найти», «Array.Find», короткое имя с дизамбигуацией |
| `platform_search` | поиск по названиям тем (RU/EN) |
| `platform_get_document` | полный текст темы (без версии — самая свежая сборка) |
| `platform_versions` | какие сборки загружены и сколько тем |

## Типовые сценарии

- **«Что за объект и как устроен»**: `get_object` → `list_routines` → `read_routine`.
- **«Где считается X»** (формулировка словами): `fts_search("расчет себестоимости")` — BM25
  выведет расчётные рутины наверх. Точная строка/идентификатор — `search_code`.
- **Ревью своей ветки**: `changed_objects(ref="origin/main")` → `review_set(ref="origin/main")` —
  сразу видно, какие рутины задеты, кто их вызывает и какие обработчики/overrides рядом.
- **Импакт правки структуры**: `find_type_usages` + `get_dependencies` + `writes_to(register=...)`.
- **Расширение против базы**: `find_overrides(kind, name)` → `read_routine(..., source="<расширение>")`.
- **API платформы**: `platform_docinfo("ТаблицаЗначений.Найти")`; не помните имя — `platform_search`.

## Индексы

| Индекс | Что даёт | Цена (реальная УТ: база + 2 расширения) | Обновление |
|---|---|---|---|
| FTS5 (`fts_search`) | ранжированный поиск по ~267k рутин/карточек | ~3.4 мин, ~1 ГБ в `~/.onec-lite/fts/` | инкремент по mtime; авто-дообновление при поиске (раз в ≥30 с), `built_at` в каждом ответе |
| Справка платформы | лукап/поиск по ~25k тем на версию | ~1 с на версию, в памяти | лениво при первом запросе или кнопкой |

Оба индекса живут **вне рабочей копии** — `git status` разработчика остаётся чистым.
Без построенного FTS-индекса `fts_search` вернёт понятную ошибку, остальное работает.

## Какой поиск выбрать

| Вопрос | Инструмент |
|---|---|
| Точная строка, идентификатор, regex | `search_code` |
| «Где про это в коде?» словами, нужна релевантность | `fts_search` |
| Найти объект по имени/синониму | `search_metadata` |
| Смысловой поиск, синонимия, документация ИТС | **большой** сервер (`hybrid_search`) |

## Траблшутинг

| Симптом | Решение |
|---|---|
| `search_code` медленный, в ответе `engine: python` | ripgrep не найден: `winget install BurntSushi.ripgrep.MSVC`, либо путь в админке / `ONEC_LITE_RG` |
| «Workspace не сконфигурирован» | `onec-lite admin` → задать корень; или `--root` / `ONEC_LITE_ROOT` |
| Порт 8010 занят | `onec-lite admin --port 8011` (или `ONEC_LITE_PORT`) |
| «FTS5 недоступен в этой сборке Python» | редкая сборка sqlite3 без FTS5 — используйте `search_code`, остальное не затронуто |
| Правки не видны | кэши инвалидируются по mtime/TTL ≤15 с; мгновенно — «Сбросить кэши» в админке |
| Админка отвечает 404 | она opt-in: режим `admin`, флаг `--admin` или `ONEC_LITE_ADMIN=true`; транспорт http |

## Совместная работа с большим сервером

Большой onec-vecgraph и так работает со **всеми** репозиториями сразу — они живут арендаторами
в одном Neo4j, арендатор выбирается заголовком `X-Tenant-Id`/bearer-токеном при регистрации.
Типовая связка в сессии: **lite = живая копия текущего репо** (свежесть, git, ревью ветки),
**big = все конфигурации разом** (семантический поиск, ИТС/стандарты, кросс-конфигурационные
вопросы). Регистрируются оба; big можно так же приколоть к проекту через project-scope
с разными токенами. Подробности подключения big — [MCP_USAGE.md](MCP_USAGE.md).

## Lite или большой сервер?

| | onec-lite | onec-vecgraph (big) |
|---|---|---|
| Данные | живая рабочая копия, всегда свежие | снимок в Neo4j (индексация оператором) |
| Инфраструктура | нет (uv + stdio/http) | Docker: Neo4j ~12 ГБ RAM, GPU для векторизации |
| Поиск | rg + FTS5 BM25 (лексический) | векторный + полнотекст + RRF (семантика) |
| Кому | разработчик на своей машине, ревью ветки | команда/агенты: BA, СА, архитектор, ревьюер |
| Уникальное | git-осведомлённость, `get_service`/`get_form`, нулевой старт | ИТС/артефакты/стандарты, мультиарендность+auth, GraphRAG, `:Detail`, overlay |
| Гид | этот документ | [MCP_USAGE.md](MCP_USAGE.md) |

Они не конкурируют: lite — «здесь и сейчас» у разработчика, big — общая память команды.
Один и тот же BSL-парсер и парсеры метаданных гарантируют согласованность результатов.
