# onec-lite против компетентного grep: замер

Стенд: УТ (база + 4 расширения, 14 942 .bsl), tiktoken cl100k, медиана из 3 прогонов,
`ref=HEAD~5`. Воспроизведение: `uv run --no-sync python scripts/bench_tools_vs_grep.py --runs 3`.

## Что сделано, чтобы числам можно было верить

Первые версии этой таблицы были подтасованы, причём каждый раз в пользу MCP. Что исправлено
(находки трёх независимых критиков):

* **токенизатор** — tiktoken, а не `len/3`: прокси занижал расход в полтора раза;
* **равный корпус** — rg ищет по всем источникам воркспейса, включая расширения (раньше только
  по базе);
* **компетентный grep** — агенту разрешены конвейеры (`grep -v`, `sort|uniq -c|head`), а команды
  сужены на каталог объекта: неограниченный grep по всей конфигурации давал MCP фиктивные
  ускорения (на `list_routines` — x3811 вместо реальных x3);
* **вопрос имеет ответ у обеих ветвей** — `find_overrides` мерился на объекте БЕЗ перехватов:
  MCP отдавал пустой ответ (36 токенов), grep — 20 нерелевантных строк, и строка показывала
  x43 в пользу MCP. Теперь объект с 62 перехватами;
* **холодный кэш** — сбрасывался только «грязный» git-набор, а разобранные модули, строки, индекс
  перехватов и git-списки выживали: «живой темп» был горячим замером;
* **провал не выглядит нулём** — пустой stdout при ошибке заменяется на текст ошибки, иначе
  неработающая команда получала «0 токенов» и выигрывала.

Два режима времени: **живой темп** — холодные кэши процесса (первый вопрос в сессии);
**подряд** — второй такой же вызов (агент задаёт серию вопросов по одной области).

## Как это читать

* **Токены: grep дешевле в 1.6 раза** (31.1k против 49.0k на 13 вопросах). MCP платит за
  структуру ответа — JSON-обвязку, координаты рутин, сводки. Дешевле он только там, где сам
  агрегирует (`writes_to`, `get_object`, `fts_search`) — то есть где grep пришлось бы дочитывать
  файлы, а этот дочит в замере не учтён (значит перевес grep здесь ЗАВЫШЕН).
* **Скорость на холодном кэше — паритет с провалами на git-вопросах**: MCP быстрее на
  `get_object` (x687), `list_routines` (x3), `fts_search` (x1.6), `find_callers`/`find_routine`
  (x1.2–1.5), но медленнее на `review_set` (x0.19), `changed_objects` (x0.21) и `find_overrides`
  (x0.1) — там он делает существенно больше работы, чем сравниваемая команда.
* **Внутри сессии MCP вне конкуренции**: второй вызов — 0.002–0.06 с против 0.1–1.5 с у grep.
  Именно этот режим и наступает, когда агент задаёт серию вопросов по одной области.
* **Качество этой таблицей НЕ измеряется.** Предикат приёмки записан у каждого вопроса, но
  харнес не проверяет, что вывод ему удовлетворяет. Полнота и корректность проверяются отдельно:
  `scripts/validate_lite_answers.py --parser-audit --index-audit`.

Вывод для маршрутизации: см. блок «Grep или MCP» в инструкциях сервера
(`src/onec_vecgraph/lite/server.py`) — он опирается на эти числа.
