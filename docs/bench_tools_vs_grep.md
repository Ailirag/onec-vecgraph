# onec-lite против компетентного grep: замер

Стенд: УТ (база + 4 расширения, 14 942 .bsl), tiktoken cl100k, медиана из 3 прогонов,
`ref=HEAD~5`. Воспроизведение: `uv run --no-sync python scripts/bench_tools_vs_grep.py --runs 3`.

## Почему этой таблице можно верить больше, чем предыдущим

Замер переделывался четыре раза, и КАЖДЫЙ раз находилась подтасовка — всегда в пользу MCP.
Полный список исправленного (находки трёх независимых критиков):

* **токенизатор** — tiktoken, а не `len/3`: прокси занижал расход в полтора раза;
* **равный корпус** — rg ищет по всем источникам воркспейса, включая расширения (было: только база);
* **компетентный grep** — конвейеры разрешены, команды сужены на каталог объекта: неограниченный
  grep по всей конфигурации давал MCP фиктивные ускорения (`list_routines` — x3811);
* **у вопроса есть ответ в обеих ветках** — `find_overrides` мерился на объекте БЕЗ перехватов
  (MCP отдавал пустоту в 36 токенов, grep — 20 нерелевантных строк, строка показывала x43);
* **фильтр объявлений в grep реально работает** — `grep -v -E "^[^:]+:[0-9]+:…"` не матчит
  windows-путь (`[^:]+` останавливается на `H`), и 17 из 20 «мест вызова» у grep были
  объявлениями: он выигрывал по токенам потому, что отвечал неверно;
* **grep дочитывает то, без чего не ответил** — на «текст рутины» он отдавал координаты
  объявления (92 токена против 1850), то есть ссылку вместо содержимого; теперь читает тело;
* **первый вопрос — действительно первый** — сбрасывались кэши разбора, но кэш листингов и
  объектов живёт в самом `Workspace`, а харнес прогревал его ДО замера (1.8 с). Отсюда были
  фиктивные x687 у `get_object` и x3 у `list_routines`;
* **провал не выглядит нулём** — пустой stdout при ошибке заменяется текстом ошибки, иначе
  неработающая команда получала «0 токенов» и выигрывала.

Два режима времени: **живой темп** — Workspace создаётся заново на каждый замер (честно первый
вопрос сессии); **подряд** — второй такой же вызов.

## Как это читать

**По токенам grep дешевле примерно в 1.4 раза** (35.2k против 49.2k на 13 вопросах). Дешевле он
почти везде, где ответ — это список координат. MCP дешевле там, где сам собирает ответ из
нескольких файлов: `get_object` (x1.35 — он ещё и сливает три копии объекта, grep оставляет
слияние агенту), `writes_to` (x1.11).

**По скорости на ПЕРВОМ вопросе сессии MCP в основном проигрывает.** Он платит прогрев рабочей
копии (~1.8 с на УТ) и построение своих структур: `list_routines` x0.04, `get_object` x0.07,
`find_overrides` x0.09, `review_set` x0.10, `changed_objects` x0.17, `read_routine` x0.46,
`writes_to` x0.58, `find_type_usages` x0.71. Быстрее он только там, где отвечает из готового
индекса: `find_routine` x2.18, `find_callers` x1.2-1.3, `fts_search` — паритет.

**Со второго вопроса картина обратная**: 0.002-0.1 с против 0.1-1.9 с у grep, то есть на порядок
и больше. Исключения — `review_set` (1.32 с) и `find_type_usages` (0.80 с): они остаются
медленнее grep даже прогретыми.

**Важная оговорка в пользу MCP:** прогрев рабочей копии платится ОДИН раз на сессию, а колонка
«живой темп» списывает его на каждую строку. Поэтому реальная сессия выглядит так: первый вопрос
дороже grep на 1-3 с, все последующие — дешевле по времени на порядок. Чем больше вопросов по
одной области, тем сильнее перевес MCP по скорости и тем заметнее его перевес по расходу токенов
в обратную сторону.

**Качество этой таблицей НЕ измеряется.** Предикат приёмки записан у каждого вопроса, но харнес
не проверяет, что вывод ему удовлетворяет — именно поэтому подтасовки жили так долго. Полнота и
корректность проверяются отдельно и другими инструментами:
`scripts/validate_lite_answers.py --parser-audit --index-audit`.
