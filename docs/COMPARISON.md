# onec-lite и другие MCP для 1С: что сравниваем

[README](../README.md) · [Руководство lite](LITE_USAGE.md)

Проверка публичных описаний: **2026-10-07**. Исходная проверка нашего кода: `e3bdef65b9403299631ce4b4b4a802ab81ab50e2`.
При подготовке публикации контракт workspace сверён с `9f22b95`: каждый MCP-инструмент,
кроме `list_workspaces`, требует явного непустого `workspace`, включая справку и `list_kinds`.
Заголовки, env и CLI-предвыбор его не заменяют. Общий workspace справки настраивает
оператор конкретного развёртывания; встроенного общего workspace/fallback в lite нет.
Это сравнение назначения и подтверждённых контрактов, **не новый независимый бенчмарк**.
Сведения о сторонних продуктах ниже взяты из их публичной документации, закреплённой
на коммитах; запуск актуальных сторонних серверов в рамках этой проверки не выполнялся.
Неописанная в источнике возможность означает «не проверено», а не «отсутствует».

## Краткая матрица

| Решение | Основной источник и задача | Поиск / анализ | Когда выбирать |
|---|---|---|---|
| **onec-lite** | Своя рабочая копия XML/EDT, база + расширения; свои `.hbk`; дополнительные исходники БСП | Эвристический BSL-парсер, метаданные, rg, FTS5/BM25, git-ревью; без эмбеддингов | «Что реально есть в этой ветке и кто это вызывает?» |
| **onec-vecgraph (big)** | Снимок конфигураций и документационные корпуса в Neo4j | Векторы + полнотекст + RRF, граф зависимостей и GraphRAG | Общий сервис поиска и знаний; нужен отдельный цикл индексации |
| **code-index-mcp / bsl-indexer** [C1] | Индекс исходников разных языков; сборка `bsl-indexer` добавляет 1С | Rust, tree-sitter, SQLite; отдельный фоновый индексатор и читающий MCP-сервер | Межъязыковая навигация, индекс символов, BSL/метаданные через один сервис |
| **1C-docs-mcp** [C2] | Синтаксис и руководства платформы; отдельные коллекции стандартов и XML-форматов | `docinfo` — точное имя; `docsearch` — hybrid vector + BM25; `standards` / `formatspec` — отдельные инструменты | «Какой API/формат нужен и как он документирован?» |
| **1c-ssl-mcp** [C3] | Документация БСП | `ssl_search`: точный идентификатор или hybrid semantic + BM25, полная запись по `doc_id`, пагинация | «Как документирован механизм БСП?» с последующей сверкой версии и кода проекта |

### code-index-mcp: пересечение не ограничивается поиском BSL

Публичный README [C1] подтверждает поддержку XML Конфигуратора и EDT `.mdo`,
аннотаций расширений, обработчиков форм, подписок, связей данных и регистраторов.
В нём перечислены, в частности, `get_object_structure`, `get_object_profile`,
`get_form_handlers`, `get_event_subscriptions`, `get_register_writers`,
`find_references`, `get_role_rights`, `bsl_sql`, а также общие `get_callers` / `get_callees`.
Есть HTTP и stdio, несколько репозиториев по алиасу; для запросов нужен работающий
фоновый индексатор. Нельзя описывать его как «только grep» или «без поддержки EDT».

У lite отдельные подтверждённые сценарии — слияние заимствованных объектов с базой,
`review_set` (diff → рутины → вызывающие), workspace-справка `.hbk`,
дополнение части индексных ответов свежими файлами. Это описание **наших** возможностей,
а не доказательство отсутствия аналогов у code-index. Полнота разрешения вызовов,
слияние расширений, задержки и стоимость контекста требуют одинаковых контрольных задач.

### Docs и SSL: разные корпуса, а не замена исходникам

В `1C-docs-mcp` поиск `docsearch(scope="all")` по каталогу [C2] не охватывает
`standards` и `formatspec`: у них отдельные маршруты. У lite `platform_search`
ищет по названиям **и полному тексту** тем локальной справки, с лексическим
переранжированием — старое описание «только заголовки» к текущему коду неприменимо.
Но это не равенство со встроенными руководствами, стандартами и спецификациями другого продукта.

`fts_search` по исходникам БСП отвечает о коде подключённого корпуса; `ssl_search`
отвечает по документации БСП. Даже одинаковое имя метода не доказывает одинаковую версию,
состав корпуса или применимость к проекту. Сохраняйте версию источника и проверяйте
найденные сигнатуры в целевой платформе/конфигурации.

Read-only поиск также не означает, что вся поверхность сервера read-only:
в публичном каталоге SSL [C3] есть **`plugin_reload`**, меняющий поведение сервера.
Для рядового потребителя следует отделять поиск от операций обслуживания.
Лицензии, цены, право общего корпоративного использования и доступные версии корпусов
уточняются у поставщика; здесь нет утверждений о тарифах или бесплатной замене.

## Что показали прежние сравнения

Ниже — **исторические результаты, восстановленные из журнала исследования**, а не
повторный прогон и не публично воспроизводимый benchmark suite: исходный корпус,
полные raw-ответы и закреплённые digest сторонних образов здесь не опубликованы.
Поэтому эти наблюдения нельзя превращать в гарантию качества или рекламное превосходство.

### 2026-09-28: onec-lite против 1C-docs-mcp и 1c-ssl-mcp

В итоговом повторном прогоне сравнивали 15 одинаковых запросов; критерий — ожидаемый ответ
в Top-5. В журнале зафиксирован onec-lite из `main`, коммит `2c402e6`.
Это **повторный** прогон после доработки поиска; более ранний результат того дня
«0/5 по естественному языку платформы» не описывает эту версию.

| Группа запросов | Профильный сторонний MCP: Top-5 / первое место | onec-lite: Top-5 / первое место |
|---|---|---|
| Платформа, точные имена (3) | 3/3 · 3/3 | 3/3 · 3/3 |
| Платформа, естественный язык (5) | 5/5 · 1/5 | 4/5 · 1/5 |
| БСП, точные имена (2) | 2/2 · 0/2 | 2/2 · 2/2 |
| БСП, естественный язык (5) | 5/5 · 3/5 | 5/5 · 4/5 |

Единственный промах lite в этой небольшой выборке — вопрос про управляемую блокировку.
Это не оценка всех механизмов платформы. Задержки из того прогона не используются
для ранжирования: сторонние сервисы вызывались через SSH-туннель, lite — локально.
Корпуса также различались: код проекта и документация библиотеки не взаимозаменяемы.

Практический вывод остаётся узким: точные имена и фактическую реализацию удобно проверять
в lite; документационный/семантический поиск полезен как дополнительный источник,
особенно когда неизвестно имя API. «Lite полностью заменяет Docs/SSL» из этого не следует.

### 2026-08-05: code-index-mcp

Исторический пилот использовал `bsl-indexer v0.47.0`. Первоначальное сравнение скорости
по чужому README было пересмотрено после учёта **полной** индексации, включая BSL-слой;
исправлялся и независимый эталон подсчёта вызовов. Этот опыт — причина не сравнивать
скорости разных стадий и не выдавать результаты разных корпусов за прямой benchmark.

По итогам исследования в lite добавили `bsl_sql` и быстрый git-инкремент
([коммит `9048d90`](https://github.com/Ailirag/onec-vecgraph/commit/9048d90)).
Поэтому старый тезис «SQL-агрегаты есть только у code-index» уже неверен.
Старые наблюдения о HTTP, количестве инструментов и времени прогрева также не переносятся
на нынешние версии без повторной проверки. Текущий публичный README code-index [C1]
описывает HTTP как штатный общий процесс.

Отдельное прежнее сравнение MCP с rg сохранилось в
[bench_tools_vs_grep.md](bench_tools_vs_grep.md) и
[карте маршрутизации](LITE_USAGE.md#rg-или-mcp-карта-маршрутизации).
Его множители относятся к тем задачам, корпусу и методике, а не ко всем проектам и конкурентам.

## Как повторить сравнение честно

1. Закрепить коммиты/образы, версию платформы/БСП, состав базы и расширений; не публиковать секреты.
2. Снять реальный `tools/list`, профиль, схемы и параметры запроса. Не смешивать ограничение окна
   с полным числом результатов, а ошибку/`daemon_offline` — с нулём найденных вызовов.
3. Для кода использовать один корпус; для справки явно отметить различие источников.
   Разделить точное имя, естественный язык, структурные связи, SQL-агрегаты и ревью diff.
4. Проверить эталон независимо от сравниваемых парсеров; фиксировать Top-1/Top-5, полноту,
   ложные совпадения, усечение и свежесть, включая изменение/удаление файла после сборки.
5. Развести cold/warm start, построение ядра/метаданных и сетевой транспорт.
   Токены считать вместе со схемами инструментов и инструкциями, не только телом ответа.
6. Сохранить обезличенные запросы, ответы и скрипт. Без этого результаты — локальные наблюдения.
